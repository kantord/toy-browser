# Releasing the engine: licences, names, what blocks publishing

Findings from checking the repository, 2026-10-09. The decisions are the owner's;
each section ends with what I would do.

## Licences

- **This project** is `MIT OR Apache-2.0` (`LICENSE-MIT`, `LICENSE-APACHE` at the
  root and in `vendor/`).
- **Vendored Blitz** (`vendor/blitz-dom`, `vendor/blitz-html`) is the same licence,
  so the copy adds no obligation beyond keeping notices and marking changed
  files. All 41 vendored `.rs` files carry the origin header (checked: none
  without `SPDX-License-Identifier`); `vendor/README.md` lists the changes.
- **Dependencies** (`cargo metadata`, 37 distinct licence strings, all permissive
  or file-level copyleft):
  - Almost everything is MIT / Apache-2.0 / Unicode-3.0 / BSD / Zlib / Unlicense.
  - **MPL-2.0** (14 crates): the Stylo family (`stylo`, `selectors`, `cssparser`,
    `app_units`, `to_shmem`, `uluru`, …). File-level copyleft: using them
    unmodified, as dependencies, puts no obligation on this project's own
    files. Modifying one of them (in `vendor/` or a patch) would require
    publishing that file's source under MPL-2.0. None is modified now.
  - `r-efi` offers `MIT OR Apache-2.0 OR LGPL-2.1-or-later`: take MIT.
  - No GPL, AGPL or "no licence" crate.
- **Pages**: the engine renders pages it did not write; nothing of theirs is stored.

Do: add a `cargo deny` licence check to CI (allow-list the strings above) so a
copyleft dependency cannot arrive unnoticed; ship a `THIRD-PARTY-LICENSES` file
generated by `cargo about` with binaries.

## What blocks publishing to crates.io

- **Path dependencies on `vendor/`.** `browser` and `engine` depend on
  `blitz-dom` / `blitz-html` by path. crates.io rejects path-only dependencies.
  Either publish the forks under new names (`<name>-blitz-dom`, keeping the
  licence and origin headers), or upstream the changes (`vendor/README.md`
  lists seven; `net.rs` image-size reading is the one that matters) and depend
  on the published crates again. Until then the engine can be used from git, not
  from crates.io.
- **Workspace layout.** `cli`, `e2e` and the Playwright tests are not part of a
  library release; keep them `publish = false`.

## Names

All of `toy-browser`, `toy-browser-engine`, `toy-browser-host`, `toy-browser-tui`
are free on crates.io today (checked), as are `celldom`, `cellhtml`, `htmlcells`,
`tuihtml`, `cellweb`, `termdom`, `cellscape`. "toy" undersells a rendering
engine that other programs are meant to build on; I would keep `toy-browser` for
the demo browser and name the library parts for what they are:

| now | proposed role |
| --- | --- |
| `toy-browser-engine` | DOM + JavaScript (QuickJS) |
| `toy-browser` | page, layout and scene (the "browser") |
| `toy-browser-tui` | HTML to a grid of cells |
| `toy-browser-host` | the grid behind a pipe (protocol v1) |

Pick one stem for the three that matter to outsiders (for example `cell…`) and
rename once, before the first publish; renaming a published crate is not
possible, only abandoning it.

## Versioning

Everything is `0.1.0` (`workspace.package.version`). The host protocol has its own
number (`protocol: 1`, `docs/host-protocol.md`); crate versions follow semver
from the first publish, and a protocol bump is a major version of the host.
